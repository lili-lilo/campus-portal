## 1. 全局定位类

### A1 — DOCX 与 `docs/` 是两份不同项目
- **结论**：DOCX 仅作为**需求素材来源**（功能清单、栏目表、角色表），交付形态以 `docs/` 的 **6 周作品集版**为准。
- **明确不做**：30 周瀑布排期、等保二级/三级测评、2000 并发、99.9% 可用率、双机热备、灰度发布、内容迁移、UAT 签字、培训视频、运维月报。
- **保留引用**：DOCX 第 2 章功能清单、表 2 角色定义、表 4/5/6 的 P0 功能点（见 A35）。
- **理由**：项目已取消、无甲方，目标为作品集宣传；30 周口径下的任何指标都无法在 6 周内验证，写进文档只会成为"未兑现的承诺"。
- **影响面**：`06-开发排期`、`11`、`12`、`13`、`15`（不新建 30 周计划）、README 的"范围说明"章节。

### A2 — 技术栈冲突（Java/PHP/.NET + MySQL + ES vs Next.js + Prisma + Supabase）
- **结论**：采用 **Next.js 全栈**。DOCX 表 8 的 Java Spring Boot / PHP Laravel / .NET、MySQL 8.0、Elasticsearch、Redis、MinIO、Nginx+Keepalived、K8s、Prometheus **全部不采用**。
- **理由**：作品集需要"一个仓库、一条命令、零成本部署"，多语言后端 + 中间件集群会直接吃掉 6 周中的 4 周。
- **影响面**：`12-技术栈冻结`；DOCX 表 8 在项目内标记为"不适用"。

## 3. 数据模型类

### A6 — 缺 Page 模型，单页栏目无处存正文
- **结论**：新增 **`Page`** 模型，与 `Article` 平级、字段取子集：`id / siteId / channelId / title / content / cover / seoTitle / seoDescription / seoKeywords / status / sort / createdAt / updatedAt`。
- **不含**：作者、来源、标签、置顶、推荐、浏览量、审核流、版本、评论。
- **理由**：单页（学校简介、历史沿革、联系我们）与文章是两种生命周期；塞进 `Article` 会让"新闻列表"查询被迫过滤掉单页，且单页不需要评论/审核。
- **影响面**：`13-数据模型-v2`、T1.4、`[channel]` 路由分支。

### A7 — 缺附件模型，但需求与演示脚本都要求"附件下载"
- **结论**：新增 **`Attachment`** 模型：`id / articleId? / pageId? / mediaId / name / path / size / mimeType / sort / createdAt`。
- **理由**：演示链路第 2 步明确要展示附件；复用 `Media` 只能表达"素材"不能表达"某篇文章挂了哪些附件、什么顺序"。
- **影响面**：`13`、T1.4、新闻详情页。

### A8 — Media 无分类、无站点归属
- **结论**：`Media` 增加 `folder String?`（单层分类，取值 `news/carousel/dept/leader/other`）与 `siteId String?`（可空 = 全站共享）；增加 `(siteId, folder)` 复合索引。
- **不做**：多级文件夹、标签体系、引用统计。
- **理由**：媒体库演示需要"按分类筛选"，单层字段足够；多级树会让第 4 周媒体库 UI 成本翻倍。

### A9 — Comment 无 parentId，但功能范围写了"回复"
- **结论**：`Comment` 增加自关联 `parentId String?` + `parent/replies` 关系。
- **UI 范围**：后台只做"二级回复"（回复挂在顶级评论下），不做无限嵌套。
- **理由**：前台评论列表用两级缩进即可，无限嵌套在演示中收益为零。

### A10 — `User.siteId` 是裸字符串，`Site` 无反向关系
- **结论**：补成**真关系**（`Site.users User[]` ↔ `User.site @relation(...)`，`onDelete: SetNull`）。
- **同时**：因为选了 Auth.js v5，需要新增 Auth.js 标准表 **`Account` / `Session` / `VerificationToken`**（`User` 加 `emailVerified`、`image` 字段），并保留业务字段 `username / password / role / siteId / status`。
- **理由**：项目不再自研认证后，"用户表要不要兼容 Auth.js 形状"从可选变成必须。
- **影响面**：`13`、T1.4 —— 这是本裁决中对 schema 影响最大的一条。

### A11 — RBAC 无表，与"角色定义 + 菜单/操作/数据权限勾选"不符
- **结论**：做**精简版 RBAC 表**：`Role`（含 `key/name/scope: global|site|channel`）、`Permission`（`key/name/group: menu|action|data`）、`RolePermission`、`UserRole`。
- **同时保留**：`User.role` 字符串作为"默认角色/Demo 快捷角色"，seed 与演示鉴权优先读它，`UserRole` 表用于展示"权限勾选"界面。
- **明确不做**：部门管理、角色继承、字段级权限、动态菜单渲染引擎。
- **理由**：第 4 周要演示"越权拦截"，没有表就只能硬编码；但完整 RBAC 引擎对作品集是过度设计。
- **影响面**：`13`、T1.4、第 4 周 RBAC 任务。

### A12 — 审核流声明两级审核，状态机只有 4 态
> **⚠ 本节已于 2026-10-01 修订（原 7 态方案作废）。** 用户裁决：状态机定为 **6 态**，`archived` 并入 `withdrawn`，命名统一为 `pending_first` / `pending_final`；并在 `AuditRecord` 上增加 `fromStatus` / `toStatus`。逐条变化与理由见 `13-数据模型-v2.md` 第 0.1 节，完整流转表见该文件缺口 7。

- **结论（定稿 6 态）**：`draft`（草稿，编辑可改可提交）→ `pending_first`（待初审，可批可退）→ `pending_final`（待终审，可批可退可发）→ `published`（已发布）；另有两个"负面终态" **`rejected`**（已退回）与 **`withdrawn`**（已撤稿）。
  - `rejected` 的唯一出口是 `draft`（编辑改完重新提交初审）；`withdrawn` 有两个出口：`pending_first`（原样重新提交）与 `draft`（继续修改）。
  - **作废项**：原稿的 `pending` / `reviewing` 命名、以及 `archived` 状态。
- **同时**：`AuditRecord.step` 取值固定为 `submit / review / approve / reject / publish / withdraw`（删除 `archive`），并**新增 `fromStatus` / `toStatus`**，使审核时间线可直接显示状态流转、区分"初审退回"与"终审退回"。
- **理由**：功能范围与 DOCX 都写了"多级审核"，UI 只做两级但状态机必须表达清楚，否则第 4 周无法演示"退回修改"。6 态方案让状态图成为单向环（无特例分支），`rejected` 与 `withdrawn` 归口同一出口 `draft`。
- **影响面**：`13-数据模型-v2`（含 `Article.createdById` 补充）、第 4 周审核流、`AuditTimeline` 组件、seed 状态分布（`published 80 / pending_first 6 / pending_final 4 / draft 4 / rejected 3 / withdrawn 3`）。

### A13 — 回收站无 `deletedAt`，软删除无法实现
- **结论**：`Article` / `Page` / `Media` / `Comment` 统一增加 `deletedAt DateTime?`，所有前台查询默认 `deletedAt: null`。
- **理由**：这是 P2 功能能落地的最小成本；漏掉它意味着回收站只能靠物理删除，无法演示"误删恢复"。
- **影响面**：`13`、T1.4、第 4 周回收站。

### A14 — 版本管理 / 回收站的优先级与周计划冲突
- **结论**：两者**保留在 schema**（`ArticleVersion` + `deletedAt`），**第 4 周实现基础版**：版本 = 保存时自动快照（不比对），回收站 = 列表 + 恢复 + 彻底删除。
- **不做**：版本 diff UI、可视化对比、按字段回滚、回收站定时清理策略。
- **理由**：作品集要的是"有版本、能恢复"这两个动作，不是 diff 算法。

### A15 — `Article.slug` 无唯一约束
- **结论**：`slug` 改为必填，并加 **`@@unique([siteId, slug])`**；同时 `Channel` 加 **`@@unique([siteId, slug])`**、`Site.slug` 加 `@unique`。
- **理由**：SEO 静态化 URL 的前提是"一站点内 slug 唯一"；否则第 5 周做 sitemap 时会出现重复 URL。
- **影响面**：`13`、T1.4、T1.5（seed 必须生成确定性 slug）。

### A16 — 缺外键、缺索引
- **结论**：
  - 补真外键：`User.siteId → Site`、`Log.userId → User`（可空）、`Statistic.siteId → Site`（可空）、`Media.siteId → Site`（可空）、`AuditRecord.userId → User`（可空，`operator` 字符串保留用于展示）。
  - 补索引：`Statistic @@index([date])`、`@@index([siteId, date])`；`Article @@index([siteId, status, publishTime])`、`@@index([channelId, status])`；`Log @@index([createdAt])`、`@@index([type])`；`AuditRecord @@index([articleId, createdAt])`。
- **理由**：90 天统计与"文章排行"是第 5 周的图表数据源，全表扫描在本地看不出来、部署到 Supabase 后会明显变慢。

### A17 — `AuditRecord.operator` 存用户名而非 ID
- **结论**：**两者都留**：`operator String` 保持不变（时间线直接显示，seed 简单），新增 `userId String?` 真外键用于"我的待办/我的操作"过滤。
- **理由**：纯用户名无法做权限过滤，纯 ID 会让时间线组件多一次 join；作品集阶段两者并存的成本最低。

### A18 — 后台有 settings 页，但 Config 无 API、无分组
- **结论**：`Config` 增加 `@@index([group])`；后台 `/admin/settings` 按 `group` 渲染 Tab（`seo / security / contact / general`），读写走 **Server Action**（见 A24），第 5 周实现。
- **明确不做**：水印、敏感词库、IP 黑白名单、缓存刷新、备份恢复、接口密钥。
- **理由**：设置页在演示链路里不出现，做深了没人看；但 `Config` 表要留着，否则第 5 周临时加表会牵连 seed。

## 4. 路由与架构类

### A19 — `[channel]` 与静态路由优先级冲突
- **结论**：定义**保留 slug 黑名单**（`news / notice / about / departments / faculty / admissions / research / disclosure / search / sitemap`），规则三条：
  1. 静态路由优先（Next.js 天然行为，不用额外配置）；
  2. seed 生成栏目时**只允许**黑名单中 `docs/15` §6 已预留静态路由的 **8 个** slug（`news / notice / about / departments / faculty / admissions / research / disclosure`）；**`search` / `sitemap` 仍禁止**；其余任意栏目命中黑名单即**抛错终止**（T1.5 已加断言）；
  3. 后台新建栏目时校验并拒绝**全部**黑名单 slug，提示"该名称已被系统页面占用"。
- **理由**：这是 Next.js 文件路由的固有行为，不是可以"修"的 bug；唯一正确做法是让数据层不产生歧义。
- **2026-10-02 修订（v1.4，T1.5 落地时发现）**：原规则 2 写作「seed 生成栏目时**禁止**使用黑名单 slug」，与 `docs/15` §6 静态路由表「`/[site]/news` → `listArticles({channel:'news'})`」**直接冲突** —— 若没有任何 `Channel.slug = 'news'`，静态路由就查不到数据（`notice` / `faculty` / `admissions` / `research` / `disclosure` 同理）。裁决：**这 8 个 slug 由 seed 以"系统栏目"身份建立**（静态路由永远优先，`[channel]` 遇不到它们，A19 防歧义的原始目的在此不适用）；`search` / `sitemap` 没有对应栏目语义，**仍然禁止**。**后台侧规则不变**（仍拒全部黑名单）。断言按白名单实现，见 `docs/00` §8 #31。

### A20 — 单页栏目没有对应路由
- **结论**：`[channel]/page.tsx` 内按 `Channel.type` 分支：`list` → 列表页、`page` → 取 `Page` 渲染单页、`link` → 服务端 302 跳转、`form` → 渲染该栏目的 `Form`。
- **理由**：一个动态路由吃下四种类型，避免为"单页"再开一套路由树。

### A21 — 多语言与路由冲突（前台路由树无 locale 段）
- **结论**：采用 **next-intl 路径前缀方案**：`app/[locale]/(site)/[site]/...`；`zh` 为默认语言。默认语言**不带前缀**（`/main/news`），非默认语言带前缀（`/en/main/news`）。
- **同时**：中文内容路径保持 `/main/news` 形状不变，与 `05-页面路由.md` 的主干一致。
- **理由**：默认语言不带前缀，演示时 URL 干净、"切英文"的动作可见（URL 变了），效果最直观。
- **影响面**：`05-页面路由`、`13`、`15-路由规格`、T1.6。

### A22 — 缺 `middleware.ts`
- **结论**：新增根级拦截文件，**职责二合一**：(1) next-intl 的 locale 协商与重写；(2) `/admin/*` 未登录跳转 `/admin/login`。
- **⚠ 命名变更**：Next.js 16 已把 Middleware 约定改名为 **Proxy**（迁移文档 `middleware-to-proxy`），文件为 `proxy.ts`、导出函数 `proxy`。T1.6 必须先在本地脚手架核实该约定（`middleware.ts` 是否仍兼容），**以核实结果为准写入 `15-路由规格`**。
- **理由**：next-intl 与后台保护都必须在请求进入页面之前完成，这是框架唯一入口，没有替代方案。

### A23 — 缺 `app/sitemap.ts` / `app/robots.ts`
- **结论**：**两者都要**：既保留 `/[site]/sitemap/page.tsx` 作为人看的站点地图页，也新增 Next.js MetadataRoute 约定的 `app/sitemap.ts`（动态读 `Site/Channel/Article`）与 `app/robots.ts`。
- **理由**：需求里 SEO 是明确卖点，而"sitemap 页面"和"sitemap.xml"是两件不同的事，只做前者在 Lighthouse/SEO 检查里拿不到分。

### A24 — API 路由大面积缺失
- **结论**：补齐并在 `14-API契约` 定稿，读写边界统一为：
  - **后台写操作**（新增/编辑/删除/审核）→ **Server Action**（少一层接口、少一套鉴权样板）；
  - **公开读与外部消费**（列表、详情、搜索、统计、上传）→ **Route Handler**；
  - `auth/[...nextauth]` 保持 Route Handler（Auth.js 要求）。
- **补齐清单**：`users / roles / sites / pages / navigation / comments / messages / config / versions / recycle / publish / tags`。
- **明确不做**：Swagger/OpenAPI 文档、API 密钥、限流、接口调用统计。
- **理由**：后台若全部走 REST，等于把"表单 → 接口 → 表单"重复写两遍；Server Action 是 App Router 的正确姿势，也更省周数。

## 5. 功能实现类

### A25 — Fuse.js 构建时索引 vs 发稿后立刻可搜
- **结论**：**运行时检索**。主搜索走 **Prisma `contains`（标题 + 正文，按站点过滤，分页）**；**Fuse.js 只用于前台搜索框的输入建议**（前端 fetch 一份轻量标题清单后本地模糊匹配）。
- **明确不做**：PostgreSQL 全文检索、pg_trgm、中文分词、Elasticsearch、热搜词统计。
- **理由**：演示链路第 7 步"发稿 → 回前台看新文章"与第 2 步"搜索招生"必须都能立刻生效；构建时索引在发稿后必然搜不到，属于演示事故。
- **影响面**：`03-功能范围`、第 5 周搜索任务、T1.10。

### A26 — 统计没有采集层
- **结论**：**接受"种子历史数据 + 不实时采集"**。第 5 周只做 Recharts 图表展示（PV/UV 趋势、来源分布、文章排行、栏目排行），不写埋点、不加 middleware 计数、不做 `track` 接口。
- **数据说明**：图表数据全部来自 seed 生成的 90 天 `Statistic` 记录；新发布文章无浏览量增长属预期行为。
- **理由**：作品集看的是图表完成度；真实埋点会引入"计数写入放大 pageview 延迟""本地 SQLite 并发写"等与展示无关的问题。
- **影响面**：`03-功能范围`（"真做"列改为"图表真做、采集不做"）、第 5 周。

### A27 — 需求清单里大量内容不在 6 周范围
- **结论**：按三档处理，**全部在 `16-范围清单` 逐项落表**：

| 档位 | 处理 | 具体项 |
|---|---|---|
| 纳入 P0 | 真做 | 顶部导航（含二级下拉、吸顶）、快捷入口、焦点图轮播、学校要闻、通知公告标签页、院系/部门入口、页脚（含备案号/二维码/无障碍入口）、本科招生、研究生招生、就业服务、全站搜索、无障碍、多语言、响应式 |
| 降级为 P1（静态占位） | 只做静态页或列表渲染，无后台管理、无动态交互 | 学术活动、媒体聚焦、专题专栏、留学生招生、科学研究（平台/成果/期刊）、党建思政、办事大厅、校园地图、师资队伍筛选、招生就业静态子页、信息公开静态子页 |
| 明确不做 | 不实现，导航与文档中均不出现 | 人才招聘与在线投递、人才培养（本/研/留学生/继续教育四套页面）、录取查询、一卡通/教务/图书馆真实对接、图片新闻相册、视频新闻播放器、360° 全景 VR、RSS/邮件订阅、微信小程序/公众号、数据看板（无数据源）、在线留言进度查询、依申请公开流转 |

- **理由**：**P-2 原则** —— 三档分明比"什么都做一半"更像作品；被标"明确不做"的项要显式写进 README，避免面试官以为漏做。

### A28 — 测试与质量体系缺失
- **结论**：**Vitest 5.0.3**（单元 / 组件）+ **Playwright**（端到端，**只覆盖 1 条关键链路**：登录 → 新建文章 → 提交 → 审核通过 → 前台可见）。
- **明确不做**：覆盖率门槛（不设 60%）、性能压测、安全渗透、兼容性矩阵、UAT 脚本、视觉回归。
- **理由**：作品集需要"能证明我写了测试"的最小证据 + 一条防止演示当天翻车的护栏；覆盖率考核在没有甲方的情况下只会消耗周数。
- **影响面**：T1.9、`12`。

### A29 — 密码明文存储
- **结论**：**bcryptjs 3.0.3**（纯 JS，无原生编译，规避 Vercel 与 Windows 双重编译坑），rounds = 10；seed 写入时哈希，登录时 `compare`。
- **明确不做**：bcrypt 原生版、argon2、密码强度策略、登录失败锁定、验证码。
- **理由**：纯 JS 版本在演示与部署环境下零编译风险；`bcrypt` 原生版在 Windows 上是常见的安装即失败点。

### A30 — Tiptap HTML 渲染 XSS
- **结论**：前台渲染富文本时，**写入侧**用 `sanitize-html` 白名单清洗（Server Action 内做），**展示侧**用 `dangerouslySetInnerHTML` 渲染已清洗内容。
- **明确不做**：CSP 头、DOMPurify 双端清洗、图片代理。
- **理由**：演示数据是种子 + 自己发的稿，风险低但"完全不做清洗"是安全常识缺口，面试时可能被问；写入侧一次清洗是成本最低的正确解。

### A31 — Supabase 连接与 Prisma 配置缺 `directUrl`
- **结论**：Prisma 7 已把 `datasource.url / directUrl` 迁到 **`prisma.config.ts`**：
  - `prisma.config.ts` 的 `datasource.url` 使用**直连**（migrate 用）；
  - 运行时 Client 用 `@prisma/adapter-pg` + `DATABASE_URL`（**pooler 连接串**，`?pgbouncer=true&connection_limit=1`）。
- **环境变量定稿**：本地 `DATABASE_URL="file:./prisma/dev.db"`；生产 `DATABASE_URL`（pooler）+ `DIRECT_URL`（直连，仅供 `prisma.config.ts` 读取）。
- **理由**：Supabase 免费版的 pooler 不支持迁移所需的会话级操作；不区分两条串，第 6 周迁移必定失败。

### A32 — 时区未定义
- **结论**：**存储与 API 一律 UTC**；展示层统一用 `Asia/Shanghai` 格式化（封装唯一的日期格式化工具，禁止散落 `toLocaleDateString`）；`Statistic` 增加 **`dateKey String`（`YYYY-MM-DD`，按 Asia/Shanghai 计算）** 并加唯一约束 `@@unique([dateKey, siteId])`，图表聚合只按 `dateKey`。
- **理由**：90 天统计按天聚合 + Vercel 默认 UTC 运行环境，是"图表数字对不上"的经典成因；用 `dateKey` 把聚合维度从时间戳里摘出来，可一次性消除该类 bug。

### A33 — 媒体"本地存储"与 Vercel 只读文件系统冲突
- **结论**：**双实现、单接口**：定义 `StorageAdapter`（`put / delete / getUrl`）两个实现 —— `LocalStorageAdapter`（开发环境写入 `public/uploads/`，`.gitignore` 排除）与 `SupabaseStorageAdapter`（生产环境走 Supabase Storage bucket）。
- **明确不做**：自动压缩、加水印、图片 CDN 变换、多桶策略。
- **理由**：本地 `public/uploads/` 能跑通演示链路；但若不在第 1 周就把接口抽出来，第 6 周部署时媒体上传会直接 500（Vercel 文件系统只读）。

### A34 — P0 口径不一致（无障碍/多语言）
- **结论**：**无障碍与多语言都提升为 P0**，并以 DOCX 表 4/5/6 为准统一 `03-功能范围` 的优先级列。
- **理由**：两者都是"一眼可见的亮点"，且无障碍是全局地基（见 A36）。

### A35 — DOCX 表格里的 P0 未纳入
- **结论**：**全部纳入 P0**：顶部导航栏、快捷入口、焦点图轮播、学校要闻、通知公告（标签页）、院系/部门入口、友情链接（P1→随页脚一起做）、页脚、本科招生、研究生招生、就业服务、全站搜索、无障碍浏览、移动端响应式。
- **理由**：这些是"首页看起来像不像真高校官网"的决定性元素，也正是 DOCX 里唯一可低成本复用的部分。
- **影响面**：`03-功能范围`（改写 P0 清单）、`06-开发排期`（第 2 周交付物扩容）、`16-范围清单`。

### A36 — 无障碍放在第 5 周太晚
- **结论**：**设计 token 前置到第 1 周（T1.3）**，第 5 周只做"功能层"（字体缩放控件、高对比度开关与持久化、键盘导航走查、ARIA 补齐）。
- **token 必须包含**：色板、间距、圆角、阴影、断点、**焦点环样式**、**高对比度主题变量**、**字号缩放变量（100%~200%）**。
- **明确不做**：朗读（TTS）、纯文本模式、GB/T 37668 或 WCAG 认证、读屏软件全量回归。
- **理由**：焦点环与对比度是每个组件的固有属性，等第 5 周再补等于把所有已写组件重翻一遍 —— 这是本条唯一不能被压缩的理由。

### A37 — 组件清单遗漏与待装清单不准
- **结论**：待装 shadcn 组件按 `12-技术栈冻结` 的清单为准，**新增** `carousel`（HeroCarousel 依赖）、`navigation-menu`（MainNav 二级下拉依赖）、`data-table`/`table`（DataTable 依赖）、`chart`（Recharts 封装依赖）；`pagination` 等以 shadcn CLI 4.x 的实际 registry 名称为准，T1.1 时逐个 `--dry-run` 校验，装不上的写自研组件。
- **理由**：`09-组件清单` 的 25 项是按旧 registry 抄的，其中部分路径/名称已变化；以 CLI 实际输出为准比维护一份可能过时的名单更可靠。

## 6. 追加条款（第一轮评审后新增，编号续接）

### A38 — 【P0 风险】Prisma 版本分叉与 Prisma 7 破坏性变更
> **本节已于 2026-10-01 按 registry 实测结果更正。** 依据与完整数据见 `12-技术栈冻结`；实测时间戳 `2026-10-01T14:58Z~14:59Z`。

- **事实（实测）**：
  1. `prisma` CLI 的 npm `latest` 标签指向 **`8.0.0-rc.19`**（预发布，2026-09-29 发布），而 `@prisma/client` 的 `latest` 是 **`7.10.0`**（稳定，2026-08-25 发布）。直接执行 `pnpm add prisma @prisma/client` 会拉到 RC，二者版本不匹配。
  2. `prisma@7.10.0` 与 `@prisma/client@7.10.0` 的包 `type` 实测均为 **CommonJS** —— **不是 ESM**（只有 `prisma@8.0.0-rc.19` 是 `type: module`）。此处为原稿的错误，予以更正。
  3. `@prisma/adapter-better-sqlite3@7.10.0` 依赖 **`better-sqlite3 ^12.6.0`**，而 `better-sqlite3` 的 npm `latest` 是 **13.0.3**（跨大版本，不满足 `^12`）；12.x 线最新为 **12.11.1**（2026-06-15）。
  4. `@prisma/client@7.10.0` 的 `engines` 为 **`^20.19 || ^22.12 || >=24.0`**，**排除 Node 21.x 与 23.x**。
- **结论**：
  1. **显式锁 `prisma@7.10.0` 与 `@prisma/client@7.10.0`**，禁用 `latest` 解析（`@prisma/adapter-better-sqlite3`、`@prisma/adapter-pg` 同为 7.10.0，保持同批）。
  2. **`better-sqlite3` 不显式安装**，交由 `@prisma/adapter-better-sqlite3` 解析到 12.x；显式安装 13.x 会造成版本冲突。
  3. **Node 必须满足 `^20.19 || ^22.12 || >=24.0`**；T1.1 第一步执行 `node -v` 校验，不满足先升级 Node。
  4. 按 Prisma 7 的新形态书写（注意：这是**文档要求**，与第 2 点实测的包类型并不矛盾 —— 包自身是 CJS，但官方升级文档要求项目侧配置 ESM）：
     - `package.json` 加 `"type": "module"`，`tsconfig` 用 `module: ESNext`、`moduleResolution: bundler`；
     - generator 改为 **`prisma-client`**（不是 `prisma-client-js`），且 `output` 为**必填**，客户端从生成路径导入（不再从 `node_modules/@prisma/client` 导入）；
     - 连接串配置迁移到 **`prisma.config.ts`**；
     - Client 构造**必须传驱动适配器**：SQLite 用 `@prisma/adapter-better-sqlite3`，PostgreSQL 用 `@prisma/adapter-pg`。
- **回退方案**：若 Prisma 7 与 Auth.js v5 beta 无法共存，则降到 **`prisma@6.19.3` + `@prisma/client@6.19.3`**（`prev` 标签，2026-04-01 发布；`@auth/prisma-adapter` 支持的 `>=6` 范围覆盖它），并放弃本条第 4 项的四个新形态。
- **验证时点**：**T1.1 结束前必须有一次"Next 16 + Prisma 7 + Auth.js v5 同时跑通登录"的冒烟验证**；不通过就不进入 T1.4。风险编号与处置见 `12-技术栈冻结` §5（R1~R3、R9）。
- **理由**：这是本项目唯一"照文档写就会踩"的技术陷阱，且它同时影响数据层、认证层、构建配置与运行环境四个面。

### A39 — 【P1 风险】Next.js 16 的 Middleware → Proxy 改名
> **✅ 本节已于 2026-10-02 结案。** 依据为**官方随包文档**（比外部文档权威）：`app/node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md`。

- **事实（实测）**：Next.js 16 **已将 Middleware 更名为 Proxy**。随包文档首行明示：**"The `middleware` file convention is deprecated and has been renamed to `proxy`"**；文件中同时存在 `proxy.md` 与 `middleware.md`（后者为废弃说明）。
- **结论（已确定）**：
  1. **文件名：`proxy.ts`**（位于**项目根或 `src/`**，与 `app`/`pages` 同级）→ 本项目为 **`app/src/proxy.ts`**；
  2. **导出：名为 `proxy` 的函数**（或 `default` 导出），签名 `export function proxy(request: NextRequest)`；
  3. **`matcher` 仍用 `export const config = { matcher: [...] }`**（与旧 Middleware 一致）；
  4. 本项目职责二合一：**locale 协商与重写** + **`/admin/*` 会话存在性检查**（`15` §5.2/§5.3）。
- **回退**（保留未用）：若 `proxy.ts` 与 next-intl/Auth.js 任一不兼容，则改用"layout 内服务端鉴权 + next-intl 官方推荐写法"，并在 `15` 中记录原因。
- **连带结案**：`12` §5 的 **R7** 与 §6.2 冒烟表；`15` §5.1 的 **U3**。

### A40 — 文档版本冲突的处置方式
- **结论**：`docs/01~10` **保留原文不删**，作为"历史输入"；所有裁决与规格以新增的 `11`~`16` 为准，并在 `01~10` 各自开头插入一行指针（`> 本文件已被 11-裁决记录 部分修订，冲突处以 11~16 为准`）。
- **理由**：面试官可能翻 `docs/` 目录；保留原始需求文档能体现"从需求到裁决"的完整链路，比删掉更有利于展示。
