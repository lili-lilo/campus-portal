## 1. v1 → v2 变更摘要

逐条对应本次指令的缺口编号。✅ = 本次落地，⏭ = 按指令不做。

### 缺口 1 — Page 模型（单页内容）✅
- **新增模型 `Page`**：`id / siteId / channelId / slug / title / content / cover / seoTitle / seoDescription / seoKeywords / status / sort / publishedAt / deletedAt / createdAt / updatedAt`。
- **落点**：`Channel.type = "page"` 时正文存 `Page`（经 `channelId` 关联）。
- **用途**：学校简介、历史沿革、现任领导、组织机构、学校章程、联系我们。
- **与 Article 分开的理由**：单页无作者/来源/标签/置顶/推荐/浏览量/评论/审核/版本；若塞进 `Article`，所有"新闻列表"查询都要额外过滤 `channel.type != 'page'`，且单页会被文章排行、搜索、统计误纳入。
- **一对一约束**：`@@unique([siteId, channelId])` —— 一个单页栏目的历史沿革只有一篇正文，避免同一栏目下堆出多篇"历史沿革"。
- **不参与审核流**：`status` 为 `draft / published` 两态，由站点管理员直接发布（A6 明确"单页不需要审核流"）。

### 缺口 2 — Attachment 模型 ✅
- **新增模型 `Attachment`**：`id / articleId? / pageId? / mediaId? / fileName / filePath / size / mimeType / downloadCount / sort / createdAt`。
- **双宿主**：`articleId` 与 `pageId` 均可空（新闻附件 / 单页附件），`onDelete: Cascade`。
- **`mediaId` 可空**：附件可能是文档（pdf/docx/xlsx），不属于"图片/视频"媒体库范畴；有 `mediaId` 时复用媒体库文件，无则独立存储。
- **`downloadCount`**：需求与演示链路第 2 步都要"附件下载"，计数用于详情页展示与"下载排行"潜在扩展。

### 缺口 3 — Media 补字段 ✅
- **`siteId String?`**：可空 = 全站共享（如通用图标），非空 = 归属站点。
- **`folder String?`**：单层分类，取值 `news / carousel / dept / leader / other`（A8）。
- **`album String?`**：相册名，用于 `相册` 型聚合（如"校园风光"图集）；与 `folder` 正交——`folder` 是用途分类，`album` 是内容分组。
- **与 Article 的引用关系**：`Article.media Media[]` ↔ `Media.articles Article[]` —— **多对多**（一张图可被多篇文章复用），Prisma 隐式中间表。
- **`uploaderId String?` + `uploader`**：`uploader` 沿用 v1 字符串（展示用），`uploaderId` 新增真外键（"我上传的素材"过滤）；与 `AuditRecord` 的 A17 处理方式一致。
- **`deletedAt`**（A13）：媒体回收站。

### 缺口 4 — Comment 加 parentId ✅
- **`parentId String?` + `parent` / `replies` 自关联**，关系名 `"CommentTree"`。
- **`siteId` 补充**：v1 只有 `articleId`，导致后台"评论管理"必须先 join Article 才能按站点过滤；补 `siteId` 后待办列表可直接按站点查。
- **两级限制**：`replies` 只挂顶级评论（父评论的 `parentId` 必须为 null）——在应用层校验，schema 层不强制（SQLite 无法表达该约束）。

### 缺口 5 — User.siteId 改正式关系 ✅
- **`Site.users User[]` ↔ `User.site @relation(fields: [siteId], references: [id], onDelete: SetNull)`**。
- `onDelete: SetNull` 的理由：站点被删时用户不应被级联删除，降级为"无所属站点"。
- **附带（A10）**：补齐 Auth.js v5 所需字段与表 —— `User.emailVerified / image`，以及 `Account` / `Session` / `VerificationToken` 三张表。

### 缺口 6 — RBAC 真表 ✅
- **新增 4 张表**：`Role`、`Permission`、`RolePermission`、`UserRole`。
- **`Role`**：`id / name / code / siteId? / isSystem / scope / description / sort / status / createdAt / updatedAt`。
  - `code @unique`：与 `User.role` 字符串取值一致（`super_admin / site_admin / editor / auditor`），保证"快速判断"与"细粒度权限"指向同一个角色语义。
  - `siteId?`：null = 全局角色（`super_admin`），非空 = 站点角色（`site_admin / editor / auditor`）。
  - `isSystem`：内置角色不可删除，后台 UI 只读展示。
  - `scope`：`global / site / channel`，表达数据范围（A11）。
- **`Permission`**：`id / name / code / type / group / sort`。
  - `code @unique`：形如 `article.create` / `article.audit` / `menu.articles`。
  - `type`：`menu / action / data`（本次指令明确）。
- **`RolePermission`**：`roleId + permissionId`，`@@unique([roleId, permissionId])`。
- **`UserRole`**：`userId + roleId + siteId?`，`@@unique([userId, roleId])`；`siteId` 表达"该用户在该站点拥有该角色"（`super_admin` 为 null）。
- **保留 `User.role` 字符串**：作"主角色"快速判断（A11），seed 与演示鉴权优先读它；细粒度走 `UserRole → RolePermission → Permission`。
- **明确不做**（A11）：部门管理、角色继承、字段级权限、动态菜单渲染引擎。

### 缺口 7 — 审核状态补齐 ✅（已定稿，见第 0.1 节偏离说明）

- **6 态**：`draft / pending_first / pending_final / published / rejected / withdrawn`，存于 `Article.status`（String，SQLite 无原生 enum，取值写在注释里）。

#### 7.1 状态定义

| 状态 | 中文 | 含义 |
|---|---|---|
| `draft` | 草稿 | 编辑可改、可提交初审 |
| `pending_first` | 待初审 | 初审员可批、可退 |
| `pending_final` | 待终审 | 终审员可批、可退、可发 |
| `published` | 已发布 | 前台可见 |
| `rejected` | 已退回 | 编辑可改后重新提交 |
| `withdrawn` | 已撤稿 | 可重新提交发布 |

#### 7.2 完整状态流转表（8 条边）

| # | 起始状态 | 动作 | 目标状态 | 可操作角色 | 写入 `AuditRecord` |
|---|---|---|---|---|---|
| 1 | `draft` | 提交初审 | `pending_first` | `editor`（本人稿件）、`site_admin`、`super_admin` | `step=submit`，`fromStatus=draft`，`toStatus=pending_first` |
| 2 | `pending_first` | 初审通过 | `pending_final` | `auditor`（本站）、`site_admin`、`super_admin` | `step=review`，`fromStatus=pending_first`，`toStatus=pending_final` |
| 3 | `pending_final` | 终审通过并发布 | `published` | `auditor`（本站）、`site_admin`、`super_admin` | `step=publish`，`fromStatus=pending_final`，`toStatus=published` |
| 4 | `pending_first` | 退回 | `rejected` | `auditor`（本站）、`site_admin`、`super_admin` | `step=reject`，`fromStatus=pending_first`，`toStatus=rejected` |
| 5 | `pending_final` | 退回 | `rejected` | `auditor`（本站）、`site_admin`、`super_admin` | `step=reject`，`fromStatus=pending_final`，`toStatus=rejected` |
| 6 | `published` | 撤稿下架 | `withdrawn` | `auditor`（本站）、`site_admin`、`super_admin` | `step=withdraw`，`fromStatus=published`，`toStatus=withdrawn` |
| 7 | `withdrawn` | 修改后重新提交初审 | `pending_first` | `editor`（本人稿件）、`site_admin`、`super_admin` | `step=submit`，`fromStatus=withdrawn`，`toStatus=pending_first` |
| 8 | **任意状态** | 保存编辑 | `draft` | `editor`（本人稿件）、`site_admin`、`super_admin` | `step=submit`（回退语义），`fromStatus=原状态`，`toStatus=draft` |

**没有任何其它转移是合法的。** 特别是：
- `draft` **不能**直接到 `published`（必须走两级审核）；
- `rejected` **不能**直接到 `published`；
- `published` **不能**直接回 `draft` —— 必须先 `withdrawn`（见下方规则说明）。

#### 7.3 你问的四个规则（逐条明确）

**① 退回（`rejected`）后编辑改完，回 `draft` 还是直接回 `pending_first`？**

> **定稿：回 `draft`。**

- **理由（状态机简洁性）**：`rejected` 的唯一出口是 `draft`，这与 `withdrawn` 的出口完全一致 —— 两条"负面终态"归口到同一个起点。这样状态图是一张**单向环**，没有特例分支：

```
        ┌──────────────────────────────────────┐
        │                                      │
     draft ──①──> pending_first ──②──> pending_final ──③──> published
        ↑              │                     │                  │
        │              └──④──> rejected <────┘                  │
        │                        │                              │
        │                        └──────────────────────────────┤
        │                                                       │
        └───────────────────── withdrawn <──⑥───────────────────┘
                  ↑                      
                  └──⑦──> pending_first（撤稿后重新提交）
```

- **实现代价**：编辑改完后需**两步**（改 → 保存为 `draft` → 再点"提交初审"）而非一步。这是可接受的成本：真实 CMS 里"退回后修改"与"再次提交"本就是两个动作，且第 4 周的"退回修改"演示正好需要展示这两步。
- **若你更看重演示顺畅**（一步回到 `pending_first`），代价是：`rejected` 有两条出口（`draft` / `pending_first`），状态机会出现"同样改完却可能落到两个不同状态"的分支，审核待办计数也需区分两种情况。**我按简洁性选了 `rejected → draft`**；如需改为一步提交，告诉我即可。

**② 撤稿（`withdrawn`）后能否重新提交，能到哪个状态？**

> **能。`withdrawn` 有两个出口**：→ `pending_first`（直接重新提交，边 7）、→ `draft`（继续修改，边 8）。
>
> - 语义：撤稿是"暂时下架"，不是删除。原稿件内容完整保留，因此允许**直接重新进入审核**，不必先退回草稿。
> - 这与 `rejected` 的差异是刻意的：`rejected` 意味着"内容有问题、必须先改"，所以强制经 `draft`；`withdrawn` 意味着"内容没问题、只是不该挂在前台"，所以允许原样重提。

**③ 发布（`published`）后能否撤稿？**

> **能** —— 边 6：`published → withdrawn`。角色限 `auditor`（本站）、`site_admin`、`super_admin`；`editor` **无权**撤稿（撤稿是内容把关动作，与 A11 的角色划分一致）。

**④ 发布（`published`）后能否重新编辑？**

> **能，但不能原地改后直接再发布。** 规则：
> 1. `editor` 在后台点"编辑"时，若当前状态为 `published`：
>    - **先落一份 `ArticleVersion` 快照**（当前线上版本），保证可回溯（A14 基础版版本管理）；
>    - 状态转入 `draft`（边 8），同时写一条 `AuditRecord(fromStatus=published, toStatus=draft)`；
>    - 前台**立即不可见**（因为前台只查 `status = 'published'`）。
> 2. 改完必须**重走两级审核**（边 1 → 2 → 3）才能再次发布。
>
> **这样设计的后果与取舍**（需要你知道）：编辑一篇已发布文章会导致它短暂下线。对作品集是可接受的（演示时"回前台看新文章"正是这个路径）；若你希望"编辑期间旧版本继续在线"，需要引入 P2 的"草稿覆盖"机制（`published` + 独立草稿行），那会让 schema 与审核流复杂度翻倍。**当前按简单方案实现。**

#### 7.4 强制约束（实现时必须遵守）

| 约束 | 内容 |
|---|---|
| C1 | **每次状态变更必须写 `AuditRecord`**，且 `fromStatus` / `toStatus` 精确填写；不允许只更新 `Article.status` 而不留痕 |
| C2 | **不允许跨状态跳转**。服务端校验必须显式比对 `fromStatus` 与数据库当前值，不一致则拒绝（防并发双击/重复提交） |
| C3 | **`published` 状态下编辑前必须先落版本快照**（规则 ④.1），否则线上内容无法回溯 |
| C4 | `role` 为 `editor` 的用户**只能操作自己创建的稿件**（`Article` 需补 `createdById` 字段以支持该判断 —— **这是本文件新增的一处 schema 改动**，见下方说明） |
| C5 | 前台查询一律 `status = 'published' AND deletedAt IS NULL` |

> **C4 引出的 schema 补充**：`Article` 增加 **`createdById String?`**（真外键 → `User`，`onDelete: SetNull`）。原因：`editor` 的权限范围是"本人稿件"（缺口 7 的可操作角色列 + A11 的数据范围），v1/v2 原稿没有任何字段能表达"稿件归属人"，仅靠 `author String` 无法可靠判断（author 是展示用的自由文本）。**这是状态机定稿后暴露出的一个真实缺口**，已在下方 schema 中补上。

- **`AuditRecord` 增加 `fromStatus` / `toStatus`**（本次指令）：使审核时间线能直接显示"待初审 → 待终审"的流转，不必从 `step` 反推。
- **`step` 取值**：`submit / review / approve / reject / publish / withdraw`。
  - 注：边 8（任意状态 → `draft`）复用 `step=submit`，因其语义是"回到可编辑态"；若要更精确可扩展为 `edit`，但那会让 `step` 与状态转移不再一一对应。**当前保留 6 个取值。**

### 缺口 8 — Article.deletedAt ✅
- `Article`、`Page`、`Media`、`Comment`、`Attachment` 统一加 `deletedAt DateTime?`（A13）。
- 约定：所有前台查询默认 `deletedAt: null`；回收站查询 `deletedAt: { not: null }`。
- 补索引 `@@index([deletedAt])`（回收站列表是唯一会全表扫 `deletedAt` 的场景）。

### 缺口 9 — Article.slug 唯一约束 ✅

- 同时：`Channel @@unique([siteId, slug])`、`Page @@unique([siteId, slug])`、`Site.slug @unique`。
- 理由：SEO 静态化 URL 要求"同站点内 slug 唯一"，否则第 5 周 sitemap 会产出重复 URL。
- 约束：slug 不得使用保留字（A19 黑名单：`news / notice / about / departments / faculty / admissions / research / disclosure / search / sitemap`）——在 seed 与后台表单校验，schema 层不表达。

- `key @unique`：key 全局唯一，`group` 只决定 UI 归组。

### 缺口 14 — Navigation 补字段 ✅
- **`url String?`**（v1 为必填，改为可空）+ **`channelId String?`** + **`target String @default("_self")`** + **`icon String?`**。
- **与 Channel 的关系**：二者互斥语义 —— `channelId` 非空 = 指向站内栏目（`url` 由栏目 slug 推导）；`url` 非空 = 外部链接或自定义路径。应用层校验"至少一个非空"。
- **`parentId` 补自关联**：v1 有 `parentId` 字段但**没有关系定义**（Prisma 无法表达树），v2 补 `parent` / `children`（关系名 `"NavigationTree"`）。

### 其它必要补充（不在 14 条内，但为闭合关系所必需）
| 项 | 内容 | 理由 |
|---|---|---|
| `ArticleVersion.userId` | 新增可空外键 + 保留 `editor` 字符串 | 与 A17 同构；"谁改的这一版"需要可过滤 |
| `Article` 反向关系 | `Article.media Media[]` | 缺口 3 要求的"与 Article 的引用关系"需要反向字段 |
| `Channel.formId` | 新增可空外键 → `Form` | `Channel.type = "form"` 必须能定位到具体表单，否则该类型无法渲染 |
| `Channel.url` | 新增可空字符串（**v2.2 补**，U1 裁决） | `Channel.type = "link"` 必须能存放跳转目标，否则该类型无法实现；与 `formId` 同属"按 type 二选一"的类型专属字段 |
| `Channel.pages` | 反向关系 `Page[]` | 缺口 1 需要 |
| `Form.siteId` | 新增可空外键 → `Site` | 表单需按站点隔离（"招生咨询"只属于主站） |
| `FormData.status` | 新增，取值 `new / read / archived` | 表单数据管理需要"已读/未读"，v1 缺失 |
| `Navigation.channelId` | 见缺口 14 | — |
| `Site.media` / `Site.forms` / `Site.statistics` / `Site.comments` | 反向关系 | 缺口 3、缺口 5、缺口 10 的必然结果 |
| **`Statistic.siteId` 改为必填 + 哨兵值** | 见第 4 节说明 | v1 的 `@@unique([dateKey, siteId])` 在 SQLite 下对 NULL 不去重，唯一约束会失效 |

## 2. 完整 Prisma Schema

> 可直接粘贴为 `prisma/schema.prisma`。

generator client {
  // 注意：Prisma 7 用 prisma-client，不是 prisma-client-js

  output   = "../src/generated/prisma"

datasource db {
  // 开发 sqlite / 生产 postgresql。切换 provider 需改这一行并重跑 migrate。
  provider = "sqlite"
  // url / directUrl / shadowDatabaseUrl 已迁至 prisma.config.ts（Prisma 7）

## 4. 索引清单与原因

### 4.1 唯一约束

| 模型 | 约束 | 原因 |
|---|---|---|
| `Site` | `slug @unique` | URL 路径段唯一（`/main`、`/cs`） |
| `Site` | `domain @unique` | 站点域名唯一（可空） |
| `Channel` | `@@unique([siteId, slug])` | 同站点内栏目路径唯一（A15） |
| `Channel` | 无全局 slug 唯一 | 不同站点可有同名栏目（`news` 在主站与子站都存在） |
| `Article` | `@@unique([siteId, slug])` | SEO 静态化 URL 唯一（缺口 9 / A15） |
| `Page` | `@@unique([siteId, slug])` | 同上 |
| `Page` | `@@unique([siteId, channelId])` | 一个单页栏目只有一篇正文（缺口 1） |
| `ArticleVersion` | `@@unique([articleId, version])` | 版本号在文章内唯一，防并发重复快照 |
| `Statistic` | `@@unique([dateKey, siteId])` | 每日每站点一条，供 upsert 幂等写入（A32） |
| `Config` | `key @unique` | 配置键全局唯一 |
| `User` | `username @unique`、`email @unique` | 登录名唯一；Auth.js Adapter 要求 email 唯一 |
| `Role` | `code @unique` | 角色码唯一，与 `User.role` 对齐 |
| `Permission` | `code @unique` | 权限码唯一 |
| `RolePermission` | `@@unique([roleId, permissionId])` | 防重复授权 |
| `UserRole` | `@@unique([userId, roleId])` | 防重复分配 |
| `Account` | `@@unique([provider, providerAccountId])` | Auth.js 要求 |
| `Session` / `VerificationToken` | `sessionToken @unique` / `token @unique` | Auth.js 要求 |

**`Statistic.siteId` 为什么改必填**：v1 设想 `@@unique([dateKey, siteId])` 且 `siteId` 可空，但 **SQLite（以及 PostgreSQL）中 NULL 互不相等**，`(2026-10-01, NULL)` 可以插入任意多条，唯一约束形同失效 —— 而这一约束正是 A32 用来保证"每日一条、可幂等 upsert"的核心。故改为必填真外键。

**为什么不设"全站汇总"行**：曾考虑用哨兵值 `"_all"` 表示汇总，但它与 `Site` 外键冲突（`_all` 不在 `Site` 表中）。最终采用 **Q6 方案 A**：不存汇总行，图表需要"全站"时对 4 个站点求和 —— 数据量仅 360 行，聚合成本可忽略，且换回完整的引用完整性。

## 5. 时区与日期约定（缺口 12 / A32）

### 5.1 三条硬规则

| 规则 | 内容 |
|---|---|
| **R1 存储** | 所有 `DateTime` 字段（`createdAt` / `updatedAt` / `publishedAt` / `publishTime` / `deletedAt` / `expires` / `repliedAt` / `date`）**一律以 UTC 存储**。SQLite 下 Prisma 存 ISO-8601 字符串，PostgreSQL 下为 `timestamptz` |
| **R2 展示** | 展示层**统一转 `Asia/Shanghai`**，且只允许通过一个日期工具模块格式化；**禁止**在组件里散落 `toLocaleDateString()` / `new Date().getHours()` 之类的本地时区调用 |
| **R3 聚合** | `Statistic` **按日聚合只读 `dateKey`**（`YYYY-MM-DD`，按 `Asia/Shanghai` 计算），**不读 `date`**。`date` 仅供展示与排序 |

### 5.2 为什么必须这样约定

Vercel 运行环境默认 **UTC**，而项目面向中国高校（`Asia/Shanghai`，UTC+8）。若不约定，会出现典型的"数字对不上"故障：

- 北京时间 `2026-10-01 07:00` 提交的数据，UTC 是 `2026-09-30 23:00` —— 按 UTC 聚合会算进 9 月 30 日；
- 90 天趋势图的"最后一天"在 UTC 下可能只有 16 小时数据；
- 统计图表与内容发布时间显示相差 8 小时。

### 5.3 `dateKey` 的计算方式（唯一实现，写入方与查询方共用）

```
dateKey = new Intl.DateTimeFormat("en-CA", {
  timeZone: "Asia/Shanghai",
  year: "numeric", month: "2-digit", day: "2-digit",
}).format(utcDate)
// en-CA 输出形如 2026-10-01
```

**要求**：seed 生成 90 天统计、以及第 5 周统计查询，都必须调用同一函数；不得任一处自行拼接日期字符串。

### 5.4 schema 中的标注

所有 `DateTime` 字段已在第 2 节 schema 中以 `/// UTC` 注释标注（见 `Article.createdAt/updatedAt/deletedAt`、`Statistic.date`、`Statistic.dateKey`）。

### 5.5 展示层的目标格式（供第 5 周实现参照）

| 场景 | 格式 | 示例 |
|---|---|---|
| 列表页日期 | `YYYY-MM-DD` | 2026-10-01 |
| 详情页时间 | `YYYY-MM-DD HH:mm` | 2026-10-01 18:30 |
| 后台表格 | `YYYY-MM-DD HH:mm:ss` | 2026-10-01 18:30:05 |
| 相对时间 | `x 分钟前 / x 小时前 / x 天前`（超过 7 天回落绝对时间） | 3 小时前 |

| Q9 | `Channel` 的保留 slug 黑名单是否需要入库校验？ | A19 要求 seed 与后台双重校验 | 建议在 seed 中加断言，后台用 zod 校验，schema 层不表达 |

### Q6 的三种解法（**已按方案 A 定稿，此处保留决策过程**）

`Statistic.siteId` 既要外键约束、又要表达"全站汇总"，二者不可兼得。方案：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（已采用）** | `siteId` 保持外键，**取消"全站汇总"行**；汇总在查询时对 4 个站点求和 | 约束完整、语义干净 | 趋势图"全站"需聚合查询（数据量 360 行，成本可忽略） |
| B | `siteId` 去掉外键，改用普通 `String` + 哨兵 `"_all"` | 可直接查汇总行 | 失去引用完整性（与缺口 5 的精神相反） |
| C | 加 `isAggregate` 标志 + `siteId` 可空，接受 NULL 唯一约束失效，改用应用层 upsert | 表达最准 | 复杂度最高，A32 的幂等保证变弱 |

**定稿**：采用 **A**（本轮修订）。`seedStatistics()` 只生成 4 个站点 × 90 天 = 360 行；图表"全站"由查询求和。schema 与 seed 映射已同步一致。
